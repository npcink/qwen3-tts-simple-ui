# 开发与公开发布复盘

## 文档定位

本文总结 `qwen3-tts-simple-ui` 从内部原型抽取、公开安全审查、Windows/GPU
真机验收，到 GitHub Alpha 发布和 SoFile 项目页上线的过程。它记录可复用的开发
思路、失败经验和后续工作方法，不替代具体的安全审查、ADR 或验收证据。

## 原始目标与最终结果

项目的目标不是发布一套完整的 Qwen3-TTS 模型发行版，而是建立一个干净、公开、
可继续开发的本地 UI 与适配层基础。最终形成了四个相互独立的结论：

| 判断面 | 结论 |
| --- | --- |
| 源码公开 | 已完成，仓库以 `0.1.0-alpha.1` 公开 |
| 目标硬件兼容性 | 一组 Windows 11 / RTX 4090 配置已通过真机验收 |
| 运行包分发 | 未提供，模型、CUDA、SoX 与第三方运行时仍由使用者准备 |
| 公网与生产可用性 | 不支持，也没有作出生产就绪声明 |

这四个结论不能互相替代：源码能公开不等于所有硬件可用；一台机器验收通过不等于
形成兼容性矩阵；本机运行成功也不等于可以直接暴露到公网。

## 实际开发路径

### 1. 先切边界，再迁移代码

没有直接复制整个内部仓库或保留原始 Git 历史，而是从内部原型制作白名单快照。
公开仓库只接收 UI、本地 API、ASR 适配、临时音频处理、GPU 共享锁和通用启动模板。
真实主机信息、安装路径、模型、声音样本、生成结果、日志和内部运维证据全部留在
私有边界之外。

这一步的核心不是“删掉几个密码”，而是先确定公开仓库应该拥有什么。边界明确后，
清理和审查才能从一次性排查变成长期可维护的规则。

### 2. 把安全默认值写进实现

项目默认只监听 `127.0.0.1`，模型与 ASR 后端也不应直接成为网络入口。上传侧增加
大小、扩展名、容器签名和扩展名/签名一致性检查；浏览器写请求增加 Host、Origin
和 Fetch Metadata 边界检查；临时上传在成功和失败路径中都进入清理流程；GPU 使用
通过进程共享锁串行化并带有超时恢复。

这些措施并不把项目变成公网产品。它们的作用是让“本机优先、受控使用”的声明与
代码默认行为一致，降低误部署风险。

### 3. 把源码发布与硬件验收拆成两道门

公开前已经完成历史重建、Gitleaks、依赖审查、威胁建模、自动测试和匿名访问验证。
因此先发布 source-only Alpha 是合理的；Windows/GPU 真机验收继续作为独立门槛，
不能反过来阻塞源码审查和后续开发。

后续目标机器到位后，再按候选代码提交执行 CustomVoice、Base 克隆、日语 ASR、
回环监听、上传清理、输出留存、请求边界、重启恢复和 GPU 锁测试。真机结论只记录
脱敏后的必要字段，不公开账户、主机、路径、文案、原始录音、生成音频或原始日志。

### 4. 用授权样本完成真实听感闭环

自动测试只能确认格式、请求和清理逻辑，不能替代“生成结果是否可听、是否符合预期”
的人工判断。验收使用明确获授权的参考录音，先检查媒体信息和声音质量，再生成足够
长的输出供人工试听。试听通过后，Windows 主机上的参考副本、上传临时文件和生成
结果被清理，公开仓库只保留 `PASS` 级别的脱敏证据。

经验上，验收样本应包含一段连续、清晰、背景噪声较低的语音；输出也应足够长，能
观察音色稳定性、停顿、语速和长句表现。只生成几秒钟的声音虽然能证明链路连通，
却不足以判断实际效果。

### 5. 以完整证据链完成发布

发布不是把仓库改成 Public 就结束。实际闭环包括：

1. 检查当前树和可达历史中的敏感数据。
2. 在候选提交上运行单元测试、编译检查、Lint 和泄密扫描。
3. 在目标 Windows/GPU 配置上完成授权样本验收。
4. 将脱敏结果写回仓库，再通过 PR 与主分支 CI。
5. 创建明确标记为 Alpha 的预发布版本。
6. 匿名检查仓库页、Release、原始文档和提交可达性。
7. 更新 SoFile 中英文项目页，并在正式域名验证实际渲染和语言切换。
8. 清理临时分支、隔离工作树和验收主机上的临时音频。

最终需要能回答：哪段代码被测过、哪次 CI 通过、哪个 Release 对外发布、线上页面
展示了什么、工作区是否干净，以及哪些结论仍然没有被证明。

## 关键开发经验

### 边界设计比功能堆叠更重要

对带有模型、GPU、媒体文件和声音克隆能力的项目，最先确定的应该是责任边界和数据
边界。把 UI、模型运行时、内部运维、公开文档和验收证据拆开，能够同时降低许可、
安全、仓库体积和后续维护风险。

### 对每个声明准备对应证据

“测试通过”要指明是哪类测试；“Windows 可用”要指明系统、GPU 和候选提交；
“已经上线”要用正式域名验证；“没有私密数据”要同时检查当前树、可达历史和构建
产物。避免用本地测试替代 CI、用 CI 替代真机、用真机替代生产网络验证。

### 私密数据默认不进入公开证据

声音、文案、路径、账户和主机信息不因为“做了脱敏文档”就应该先进入仓库。更安全
的流程是在私有环境完成测试，只把最低必要的结构化结论写入公开记录。摘要和哈希也
可能是敏感数据，应限制在确有审计需要的私有运行目录中。

### Windows 问题必须在 Windows 上解决

本次真机验收暴露了两个本地/CI 难以替代的问题：未使用的日志文件句柄会阻止 Windows
清理，旧控制台代码页会让后端返回的 Unicode 文本触发编码错误。对应修复是延迟打开
日志文件，并让 Windows UI 明确运行在 Python UTF-8 模式。跨平台代码不能只靠 macOS
或 Linux 推断 Windows 行为。

### 先区分代码失败与基础设施失败

SoFile 合并阶段，Gitee 运行器多次在安装依赖时访问 npm registry 超时，测试根本没有
开始。日志证据表明这是依赖下载失败，不应被描述为代码测试失败。最终在流水线中加入
可访问镜像和下载重试，并以合并后的 `master` 流水线成功作为最终门禁。

另一个容易忽略的事实是：PR 流水线当时读取的是目标分支上的工作流配置，因此在 PR
分支修改流水线不能修复同一次 PR 的运行环境。以后遇到类似情况，应先确认流水线配置
的取值来源，再决定重跑、修改默认分支配置或使用受控的基础设施失败例外。

### 视觉验收必须包含交互与长页面

项目介绍页早期只检查了首屏视觉，没有覆盖完整页面高度、固定导航和中英文状态切换，
因而出现首屏之后空白、顶部菜单未固定、语言按钮无效果等问题。着陆页验收不能只看
截图；至少要检查完整滚动范围、锚点导航、固定头部、语言切换、移动端和正式域名行为。

## 可复用工作方法

### 开发阶段

- 先写清楚仓库负责与不负责的内容，再决定复制哪些文件。
- 默认把模型、媒体、运行数据、`.env`、日志和主机事实放在 Git 边界之外。
- 对上传、网络入口、留存和并发资源分别建立明确控制。
- 自动测试保持离线，不依赖真实模型和 GPU；真实硬件使用单独验收清单。

### 真机阶段

- 先确认目标账户、Python、GPU、驱动、CUDA、端口和当前运行进程。
- 所有服务先绑定回环地址，再检查 UI 到后端的实际链路。
- 只使用本人或明确获授权的样本，并先验证格式、时长和可听质量。
- 同时覆盖成功路径、失败清理、重启恢复和并发锁，而不是只听一次生成结果。
- 测试结束后列出并清理副本、上传和输出，再做剩余数量复查。

### 发布阶段

- 使用精确文件清单提交，避免把工作区中的无关修改带入发布。
- 将源码、硬件兼容、运行包、公网部署和生产就绪分别表述。
- 保持候选提交、验收记录提交、Release 和线上页面之间的可追溯关系。
- 对第三方 CI 先读日志再归因；基础设施失败需要补充本地证据和最终主分支门禁。
- 生产页面必须验证真实内容和交互；PWA/CDN 缓存场景使用缓存破坏参数辅助核对。
- 发布结束后检查远端、标签、匿名访问、临时分支、工作树和敏感运行文件。

## 工作审视报告

### 原定目标

从内部原型得到一个不泄露私密事实、可公开复用、可在真实 Windows/GPU 环境验证，
并能作为后续开发基础的独立项目；同时提供中英文项目介绍页和可追溯的发布证据。

### 完成情况

- [x] 独立公开仓库、白名单源码和干净可达历史
- [x] 本机优先的安全默认值、威胁审查和自动化测试
- [x] Windows 11 / RTX 4090 单配置端到端验收
- [x] 授权样本与生成结果不进入公开仓库，验收后完成主机清理
- [x] GitHub Alpha Release、主分支 CI 和匿名访问检查
- [x] SoFile 中英文项目页、正式域名内容和语言切换验证
- [ ] 多硬件兼容性矩阵、Windows 运行包和生产公网能力（不属于本阶段目标）

### 发现的问题

| 严重程度 | 问题描述 | 根本原因 | 改进建议 |
| --- | --- | --- | --- |
| 应当改正 | SoFile 项目页第一版只覆盖首屏，未验证长页面、固定导航和语言按钮 | 把视觉完成度当成了功能验收，缺少交互检查表 | 页面交付前固定执行全页滚动、锚点、sticky、双语、移动端和生产域名验收 |
| 应当改正 | Windows 初次生成结果过短，只能证明链路连通，不能充分判断音色和长句效果 | 真机清单最初偏重技术连通，缺少人工听感的最小样本要求 | 明确推荐的参考片段和输出时长，并把人工试听结论列为独立门槛 |
| 应当改正 | 远程验收过程中曾需要切换目标 Windows 账户后重新确认终端和进程 | 启动前没有把“当前账户与运行上下文”作为硬性前置条件 | 第一条预检命令就记录当前账户、工作目录、监听端口和 GPU 进程，账户不符时立即停止 |
| 建议改进 | Gitee PR 门禁连续三次在 npm 下载阶段失败，首次修改 PR 分支工作流未影响该 PR | 在修改前没有先确认 PR 流水线从目标分支读取配置 | 先检查流水线配置来源；为中国区运行器预设镜像、重试和较长超时，并保留主分支复验 |
| 建议改进 | EdgeOne 控制台会话未登录，无法取得本次部署 ID | 发布前没有把控制台认证状态纳入预检 | 部署前确认控制台登录；若不可用，明确降级为正式域名内容、响应头和更新时间证据，不虚构部署 ID |

### 做得好的地方

- 没有为了快速公开而导入内部历史，而是重建可审查的白名单历史。
- 在用户明确授权后才使用声音样本，公开记录始终保持最小化和脱敏。
- 把自动测试、真机生成和人工听感连接成闭环，并在完成后清理运行文件。
- 面对 CI 失败先读取日志、区分基础设施与代码问题，再用主分支成功完成证据闭环。
- 保留了 Alpha、本机优先和非生产声明，没有因为单机验收通过而扩大支持范围。

### 下次重点关注

- 开始远程真机操作前，先完成账户、端口、进程、路径和授权样本五项预检。
- 写验收清单时同时定义技术结果和人工可用性结果，避免“能生成”替代“效果可判断”。
- 页面发布把全页内容和交互检查与视觉检查放在同一门禁中。
- 第三方 CI 变更前先确认工作流配置来源、网络条件和缓存行为。
- 每次新增硬件或后端版本，只追加该配置的脱敏证据，不扩大未经验证的兼容性声明。

## 后续开发方向

建议保持“小而清楚”的项目定位，按以下顺序继续：

1. 为已知兼容后端版本建立明确的 API 契约测试。
2. 在确有需求时逐项扩展 Windows/GPU 兼容性矩阵。
3. 将运行包、模型下载和第三方许可作为独立项目评估，不直接塞入源码 Alpha。
4. 只有在身份认证、限流、审计、滥用处理和监控都具备后，才重新评估多用户或公网部署。
5. 每个阶段继续维护“代码提交 → 自动门禁 → 真机证据 → Release → 线上说明”的闭环。

项目最有价值的资产不是某一次生成结果，而是已经建立的干净边界、可重复清单和诚实
声明。后续开发应在这三个基础上增量推进。
